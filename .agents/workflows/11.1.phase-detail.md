# 🏗️ Phase Detail Workflow

Workflow này hướng dẫn AI cách bóc tách một Phase từ Master Plan và chi tiết hóa nó thành một kế hoạch thực thi có thể code được ngay lập tức.

## 📋 Quy trình thực hiện

### Bước 0: Discover Master Plan file

Chạy: `ls ./ImplementPlan/` để xem các plan files hiện có. Đọc file master plan đang active (không phải trong `Archived/`).

### Bước 1: Xác định Phase mục tiêu

- Đọc Master Plan vừa tìm được ở Bước 0.
- Xác định Phase cần chi tiết hóa.
- Hiểu bối cảnh của Phase đó trong tổng thể dự án.

### Bước 2: Tạo file Phase Detail mới

Tạo một file Markdown mới trong cùng thư mục với Master Plan, đặt tên theo format: `phase-[N]-[name].md`.

### Bước 3: Áp dụng Anatomy của Phase Detail

Mỗi Phase Detail phải tuân thủ cấu trúc sau:

#### 1. Header & Thông tin cơ bản
Mở đầu bằng mục tiêu duy nhất, mức độ rủi ro và thời gian dự kiến.

```markdown
## Phase [N]: [Tên Phase]

**Mục tiêu:** [Phase này done khi điều gì xảy ra - một câu duy nhất]
**Risk Level:** [Low/Medium/High] — [Lý do ngắn gọn]
**Duration:** ~[X] giờ
```

#### 2. Danh sách Sub-tasks (X.Y)
Mỗi sub-task phải map trực tiếp vào một file cụ thể. Không viết chung chung.

```markdown
### [N].1 [Tên Task 1]
### [N].2 [Tên Task 2]
```

#### 3. Chi tiết mỗi Sub-task (5 thành phần bắt buộc)
- **a) Context một câu:** Giải thích tại sao task này cần làm.
- **b) Code/config snippet:** Minh họa thực tế (không mô tả trừu tượng).
- **c) Quyết định kỹ thuật:** Ghi rõ các lựa chọn tại chỗ.
- **d) Constraint tương lai:** Điều KHÔNG được làm sau này để tránh regression.
- **e) 🔴 Race Condition Check:** Nếu task liên quan đến async/timing/event/state update — trả lời: *Execution order có đảm bảo? Data có thể stale? Event có thể arrive sớm? Có in-flight op cần block?* Nếu không liên quan → ghi "N/A — synchronous".

#### 4. Checklist thực thi
Danh sách checkbox phân theo layer (Setup, App Side, CSS, v.v.)

#### 5. Định nghĩa "Done" (Success Criteria)
Các tiêu chí đo lường được để xác nhận Phase đã hoàn thành.

## 🛠️ Template mẫu

```markdown
## Phase 2: Asset Handling

**Mục tiêu:** Ảnh local được upload và hiển thị đúng trên published page.
**Risk Level:** Medium — thay đổi payload format gửi lên Worker.
**Duration:** ~6 giờ

### 2.1 Phân loại asset theo kích thước
Context: Port logic từ service cũ để tối ưu payload.

```js
// publish-utils.js
const ASSET_LIMITS = {
  MAX_ASSET_SIZE: 5 * 1024 * 1024,
};
```
> **Decision:** Sử dụng 5MB làm ngưỡng để tránh timeout Worker.
> **Constraint:** KHÔNG hardcode URL — luôn đọc từ SettingsService.

### Checklist
- [ ] Sub-task 1 done
- [ ] Sub-task 2 done

**Done khi:**
- [ ] npm run lint passes
- [ ] Test case X pass
```

---

## ⚠️ Nguyên tắc cốt lõi
- **Một sub-task = một file:** Nếu liên quan > 2 file, hãy tách task.
- **Code snippet là bắt buộc:** Nếu không thể viết snippet, task đó chưa được nghĩ kỹ.
- **"Done" phải đo được:** Tránh viết "hoạt động đúng", hãy dùng "test case pass".
- **Ghi ít nhất 1 constraint:** Để bảo vệ codebase về sau.
- **Race Condition phải có câu trả lời:** Mọi task async/event đều phải có component (e) — không được bỏ trống hoặc bỏ qua.
